# 에이전틱 드로잉 전환 설계 (v1 방향)

## 1. 배경과 방향 전환

- v0는 IR JSON을 받아 `.kra` 문서를 한 번에 생성하는 일괄(batch) 컴파일러였다.
- 프로젝트 목표가 재정의되었다. 목표는 생성형 이미지 합성이 아니라, 언어 모델이 그림 도구를 하나씩 짜내어 그리는 **에이전틱 드로잉 시스템**이다.
- 근거: 창작 지시 자체가 언어적으로 이뤄지므로 언어 모델이 계획·비평·도구 선택의 주체가 되는 것이 자연스럽다.
- v0 코드는 폐기 대상이 아니라 승격 대상이다. 일괄 컴파일러는 점증적 툴콜 실행기로 재배치된다.

## 2. 핵심 원리

- 액션 하나 = 드로잉의 토큰 한 개다.
- 모델은 문서 전체를 한 번에 명세하지 않고, 살아있는 문서에 op를 하나씩 적용한다.
- 비결정성은 플래너(모델) 계층에만 격리한다. 실행기는 결정론을 유지한다.
- 모든 액션은 로깅되며 세션은 재생 가능해야 한다.

## 3. 폐루프 구조

```text
observe  -> 캔버스 렌더 + 레이어 상태 관찰
think    -> 비평 + 다음 의도
act      -> 툴콜 1개 (JSON op)
execute  -> 결정론 실행기가 Krita 문서에 적용
```

## 4. 이중 속도 루프

인간 화가처럼 인지와 운동의 시간 스케일을 분리한다.

| 루프 | 주체 | 주기 | 역할 |
|---|---|---|---|
| 느린 루프 | LLM | 논리 단위마다 | 관찰 -> 비평 -> 다음 의도 |
| 빠른 루프 | 실행기 | 즉시 | 기하 프리미티브 적용 |

- LLM은 매 붓질이 아니라 매 결정을 감독한다.
- 관련 스트로크 묶음은 하나의 액션 블록으로 합쳐 관찰 왕복을 줄인다.

## 5. 액션 프로토콜

- op 종류: layer ops / stroke ops / vector ops / mask ops / filter ops
- 스트로크는 원시 좌표 스트림이 아니라 파라메트릭 형태로 표현한다: `{브러시, 색, 크기, 투명도, 경로: 베지어 세그먼트}`
- 벡터는 SVG 조각으로 주입한다 (`addShapesFromSvg()` 재사용).
- 모든 op는 `nic_ir` 스키마·검증기를 확장해 검증한다.
- 미지원 op는 조용히 누락하지 않고 report에 기록한다 (v0 원칙 계승).

## 6. 관찰 채널

- 델타 관찰: 매 스텝 전체 캔버스를 재전송하지 않는다. dirty region만 고해상도 크롭한다.
- 숫자 신호: 변경 bbox, 색 히스토그램 변화, 레이어 통계는 저비용으로 함께 제공한다.
- 전체 렌더는 단계 경계(체크포인트)에서만 수행한다.
- VLM 호출 전 결정론 사전검증을 수행한다: 스트로크가 의도 bbox 안에 찍혔는지, 픽셀이 실제로 변했는지.
- VLM의 공간 인지 한계 보완을 위해 측정기구를 제공한다: 각도·비율·엣지를 프로그램적으로 재서 숫자로 피드백한다.
- 오래된 이력은 텍스트 요약으로 압축하고 최근 상태만 이미지로 유지한다.

## 7. 구성 요소 배치

```text
[오케스트레이터 (일반 Python 프로세스)]
  - LLM 호출, 세션 로그, 관찰 스케줄
       | localhost RPC
[Krita 플러그인 = thin 서버]
  - apply(op), snapshot(), manifest()
       |
[nic_compiler 연산 모듈] <- 기존 코드 승격
```

- 플러그인 내부에 LLM SDK를 두지 않는다. 샌드박스·GIL·의존성 문제를 피하기 위해서다.
- 플러그인은 `apply(op)`와 `snapshot()`만 노출하는 thin 서버로 축소한다.

## 8. 기존 코드 승격 계획

| 기존 모듈 | v1 역할 |
|---|---|
| `nic_ir` schema/validator | 액션 프로토콜 검증기 |
| `nic_compiler` raster/vector/mask/layer ops | RPC 핸들러 (op별 실행기) |
| `krita_session` | 서버 어댑터 + capability detection 유지 |
| `reporting` | 세션 로거 기반 |
| 일괄 컴파일 경로 | 유지 — 회귀 테스트와 시뮬레이터 검증용 |

## 9. 설계 원칙 (v0에서 계승)

- 같은 op에는 같은 결과 (실행기 결정론)
- 미지원은 조용히 누락하지 않고 보고
- 순수 Python 코어 분리 (헤드리스 시뮬레이션 가능)
- 파일 I/O workspace 경계 유지

## 10. 미결 포크

1. 루프 주인 위치: 외부 오케스트레이터 (권장) vs Krita 내장
2. 스트로크 표현 깊이: v0는 순수 파라메트릭 vs 처음부터 소형 운동모델
3. 인간 개입 지점: 매 스텝 승인 vs 체크포인트 게이트

## 11. 구현 상태 (2026-08-22)

- `src/nic_agent`: 액션 프로토콜(schema/models/validator), 결정론 실행기(executor), 헤드리스 백엔드(headless_backend + simulator), 세션 로거(session_log), 폐루프(loop/policy), 브리지 코어(bridge_core), RPC 클라이언트(rpc).
- 실행기는 `DocumentBackend` 프로토콜로 문서 조작과 분리 — HeadlessBackend(테스트·시뮬레이터)와 KritaBackend(Krita 내부)가 동일 액션 프로토콜을 소비한다.
- Krita 플러그인 `pykrita/nic_agent_bridge`: 메뉴에서 서버 기동/정지. 연결 스레드가 JSON 라인을 읽고, 메인스레드 QTimer 펌프(QueuedSubmitter.drain)가 요청을 처리해 Krita API 스레드 제약을 지킨다.
- 와이어 프로토콜: `ping / action / observe / reset / shutdown`. 액션 응답에 결과+관찰을 함께 실어 왕복 1회로 폐루프 한 스텝이 닫힌다.
- 오케스트레이터의 AgentLoop는 로컬 실행기와 원격 KritaRPCExecutor를 동일 인터페이스로 구동하며, RPC 경유 재생 산출물이 바이트 단위 동일함을 테스트로 확인했다.
- 미검증: 실제 Krita 런타임 수동 스모크(macOS 절차는 docs/07 참조).
